# ProOblik v8 — єдиний редактор проводок поточного підприємства

**Основа:** `ProOblik_v7_multi_postings_subconto.zip`. Повний ZIP містить усі файли застосунку.

## Встановлення

1. Створіть резервну копію або гілку Neon. Потрібні попередні міграції v7.
2. У **тестовій базі Neon** виконайте `MIGRATE_V8_LOCAL_POSTING_VERSIONS.sql` (лише один раз). Скрипт додає таблицю локальних версій і FK у `entries`, не переписуючи вже проведені записи.
3. Після успішної міграції замініть файли в GitHub вмістом архіву; виконайте деплой Netlify. Переконайтесь, що збережено `DATABASE_URL`, `AUTH_SECRET` та папку з власними шрифтами, якщо вона використовувалася.
4. Виконайте `VERIFY_V8_LOCAL.sql` і перевірте документ на **тестовому підприємстві**. Потім окремо звірте інше підприємство.

> Не запускайте `schema.sql` повторно поверх робочої бази. Ця версія не підключалася до реальної Neon, тож тестування в ній ще не проводилося.

## Робота в інтерфейсі

**Сервіс суперадміна → Проводки поточного підприємства.** Оберіть підприємство, знайдіть відповідну кореспонденцію й натисніть **Змінити**.

У модальному вікні:

- Дебет, кредит і «Суть господарської операції» редагуються прямо в таблиці.
- Область застосування зафіксована: **лише обране підприємство**, його назва показується у вікні.
- **Дата набрання чинності** — завтра за київським календарем; для цього конкретного редактора її змінити неможливо.
- **Причина зміни** за замовчуванням: «Уточнення кореспонденції рахунків»; поле можна відредагувати.
- **Зберегти й активувати** публікує незмінну редакцію з датою початку дії завтра. Зверху в основній таблиці сьогодні видно чинну проводку, поруч — заплановану.
- **Історія** відкриває всі локальні редакції цієї пари: дату, рахунки, зміст, автора, причину.

Наприклад, при редагуванні Дт 311 / Кт 40 на Дт 311 / Кт 401 лише для підприємства А — після дати чинності підприємство А бачить 311/401, а підприємство Б — базовий чи свій варіант. Старі проведення не переписуються. Якщо для цієї пари є старе глобальне правило, **локальна опублікована версія матиме пріоритет**.

## Де зберігається

- `company_posting_versions` — незмінні **локальні** редакції, з `company_id` та датою набрання чинності; нова редакція не видаляє попередню. Якщо на ту саму дату опубліковано кілька редакцій, діє остання за ID, а всі залишаються в історії.
- `entries.company_posting_version_id` — точна локальна редакція, яка вплинула на рядок бухгалтерського запису. Значення наявне лише там, де було застосовано локальне правило.
- `accounting_rule_versions` — наявні **глобальні** правила; вони залишаються для сумісності з v7 та формулами звітності.
- `company_posting_baseline` — попередні базові налаштування підприємства; їх не видалено, вони застосовуються тільки за відсутності локальної та глобальної версії для цієї пари. Старі зміни baseline залишаються також в `audit_log`.

## Особливості й обмеження

- Цей редактор налаштовує **кореспонденції документів** (банк, каса, склад, зарплата, закриття). Окремий довідник 472 ручних типових операцій `typical_operations` не переносився до цієї локальної моделі й поки залишається загальним.
- Активація ґрунтується на **даті документа**. Якщо перепроводити старий документ із датою до набрання чинності, використовується попередня версія; редагування самого документа зберігає стандартні перевірки та аудит.
- Загальна сума документа, автоматичний ПДВ і кількість/собівартість запасів не змінюються через довільні правила. Переназначення рахунків ПДВ та складських рахунків із вартісними/кількісними наслідками заблоковане; рахунок 23 не блокується лише через приналежність до класу 2.
- Для глобальних правил окремий сервіс **Глобальні правила та звіти** лишився доступним. У разі конфлікту опублікована локальна версія конкретної пари має пріоритет.
- Сама дата активації завтра **не означає зміну вже збережених записів**. Помилкові проведення виправляйте механізмом сторно/коригування.

## Перевірки

Додано `tests/company_posting_versions_v8.test.mjs`, який перевіряє видимість правок для двох підприємств, заплановану дату, редагування та історію. Усі попередні автоматичні тести запускалися локально. **Інтеграційний тест на справжній Neon не проводився.**
