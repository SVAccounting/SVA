# ProOblik v7 — багаторядкові проводки, початкові кореспонденції та субконто

Основа: ProOblik_v6_rule_activation_password_design(1).zip. Цей архів містить увесь застосунок, а не лише змінені файли.

## Перед встановленням

1. Створіть резервну копію/гілку бази Neon, бажано спочатку протестуйте на копії.
2. База має вже містити схему попередньої ProOblik v6 (включно із `accounting_rule_versions`, `entries_a`, `payroll_calculations`, `docs`, `stock_moves`, `users`, `audit_log`).
3. **Запустіть у Neon SQL Editor лише `MIGRATE_V7_SUBCONTO_AND_LOGIC.sql`**. `schema.sql` призначений насамперед для чистого встановлення, не запускайте його вдруге поверх робочої бази без окремої оцінки.
4. Після успішної міграції замініть код GitHub вмістом ZIP, виконайте деплой Netlify; не втрачайте чинні змінні середовища, зокрема `DATABASE_URL`.
5. Запустіть `VERIFY_V7.sql` у Neon і перевірте тестове підприємство, перш ніж виконувати реальні проводки.

## 1. Конструктор бухгалтерської логіки

**Сервіс суперадміна → Конструктор бухгалтерської логіки:**
- коригування наявних пар Дт/Кт зберігається у версіях;
- новий блок «Додаткові проводки документа» дозволяє до 30 нових рядків: окремі Дт/Кт, зміст, сума та значення субконто;
- для сум пропонується контрольована формула **основа × коефіцієнт**. Основа: `fixed` (фіксована гривнева сума), `net` (сума без ПДВ), `total` (загальна сума), `vat` (ПДВ), `cost` (собівартість), `lines_total` (сума вихідних рядків). Не виконується жодного користувацького JS/SQL;
- додаткові проводки заборонено створювати на рахунках запасів класу 2 та податкових рахунках 641–644, щоб не розійшлись складський, ПДВ та головна книга;
- для документів, що не створюють облікових проводок (`doc:inv`, `doc:ost`, `doc:mv`), довільні додаткові рядки також заблоковані;
- зміни проходять перевірку та дату активації; як і в v6, дата за замовчуванням — наступний день, сьогодні — з повторною перевіркою пароля суперадміністратора на сервері;
- попередні бухгалтерські записи автоматично не перераховуються.

**Обмеження:** це безпечні арифметичні формули з однією базою й коефіцієнтом, а не універсальний міні-Excel з умовами, агрегатами та посиланнями на довільні поля. Для спеціалізованих алгоритмів ПДВ/FIFO та розподілу за партіями потрібне розширення профільних документів.

## 2. Редагування безпосередньо в основній таблиці

**Сервіс суперадміна → Діючі проводки за операціями:** в таблиці натисніть «Змінити», введіть нові рахунки і «Суть операції» та збережіть. Дані зберігаються в новій таблиці Neon `company_posting_baseline` **тільки для вибраного підприємства**.

Пряме налаштування дозволено, поки в підприємстві немає проведень `entries`, документів `docs`, складських рухів `stock_moves` та проведених розрахунків зарплати. Далі кнопка переводить до версійного конструктора: самі історичні проведення залишаються незмінними. Від чужих підприємств це обмеження не залежить. Зміни аудіюються. Якщо ту саму початкову кореспонденцію вже змінює чинне глобальне правило, пріоритет має опубліковане правило, тому дублювання блоковане.

Це *не пряме редагування вже здійснених бухгалтерських записів* у журналі. Виправлення таких записів — через сторно/коригування.

## 3. Три субконто в обліку

**План рахунків → виберіть рахунок → Субконто 1/2/3.** Для кожного підприємства дозволено від нуля до трьох вимірів: контрагент, договір, склад, номенклатура, партія, банківський рахунок, працівник, центр витрат, проєкт, документ або довільне текстове значення. Налаштування зберігаються в Neon як `account_subconto_settings`.

- Для **кожної проведеної проводки** зберігаються окремі *знімки значень* `debit_subconto` і `credit_subconto`. Зміна довідника не переписує старі записи.
- Автоматичне заповнення працює, коли джерельний документ містить відповідні відомості (наприклад, контрагент, номенклатура, склад). У ручних проводках є окремі поля для Дт і Кт.
- У конструкторі додаткової проводки можна задати позиційні значення трьох субконто для обох сторін, а також шаблони `{counterparty}`, `{item}`, `{warehouse}`, `{staff}`, `{project}` тощо.
- Журнал відображає субконто; у **Звіти → Обороти за субконто** є обороти й сальдо за рахунком, номером субконто й датами.
- При сторнуваннях перенесені значення субконто вихідних проводок.

**Важливі обмеження аналітики:** значення наразі текстові, а не повноцінні ID-ключі довідників. Попередні записи не заповнюються заднім числом. Під час FIFO зі списанням кількох партій один агрегований запис може не мати однозначної партії: точні кількості/партії, як і раніше, потрібно звіряти у складських регістрах. Рядки старих типових операцій можуть потребувати ручного вводу субконто. Додаткові субконто не запускають автоматично нових рухів складського обліку.

## Що перевірено / що ні

Запущено синтаксичну перевірку JavaScript і локальні автоматичні тести ProOblik (склад, регістри, конструктор, модулі, а також нові тести v7 для багаторядкових правил і субконто).

**Не перевірено** виконання SQL-міграції на робочому Neon, браузерний сценарій із реальними даними та фінансову правильність усіх можливих облікових конфігурацій. Робочу базу Neon та репозиторій GitHub ця підготовка не змінювала.
