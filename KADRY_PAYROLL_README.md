# ProOblik: Кадри, нарахування, відомість і виплати

## Порядок оновлення
1. Створіть резервну копію production-бази Neon і протестуйте на окремій гілці Neon/сайті Netlify.
2. Якщо `payroll_migration.sql` ще не виконувався, запустіть його першим.
3. Запустіть `payroll_workflow_migration.sql` через Neon SQL Editor.
4. Завантажте файли цього архіву в GitHub, дочекайтеся Deploy Netlify; оновіть сторінку Ctrl+F5.
5. У **Кадри → Податкові нормативи** заповніть рік, прожитковий мінімум на 01.01, мінімальну зарплату, ставки ПДФО, ВЗ і ЄСВ; перевірте згідно чинних норм.
6. У **Кадри → Персонал** перевірте ПСП, % ПСП, ставку ЄСВ (індивідуальна за наявності) і рахунок витрат на зарплату (за замовчуванням 92).
7. У **Кадри → Нарахування зарплати** створіть розрахунок, задайте першу половину (друга перераховується), натисніть **Провести** після звірки.
8. У **Кадри → Зарплатна відомість** виберіть рік/місяць, натисніть **Виплатити ЗП**, **Сплатити податки** або **Виплатити все**. Ці кнопки готують проєкти платіжних інструкцій і НЕ перераховують гроші.
9. Після реального виконання банком перевірте виписку та натисніть **Підтвердити за випискою** для кожної інструкції — програма сформує бухгалтерські проводки.

## Проводки
- Дт 92 (або рахунок із картки працівника) Кт 661 — зарплата (брутто).
- Дт 661 Кт 641 — утриманий ПДФО.
- Дт 661 Кт 642 — утриманий військовий збір.
- Дт 92 (або рахунок із картки працівника) Кт 651 — ЄСВ роботодавця.
- Дт 661 Кт 685 — додаткові утримання (рахунок за умовчанням; бухгалтер має підтвердити правильність конкретного виду утримання).
- Після підтвердження банківського виконання: Дт 661/641/642/651 Кт 311 — відповідно зарплата, ПДФО, ВЗ, ЄСВ.

## Межі та застереження
- Виплати реально НЕ надсилаються до банку; платіжні інструкції — внутрішні проєкти для звірки і ручного перенесення/обробки. Для справжніх банківських платіжних документів обов'язкові IBAN, ідентифікація отримувача, призначення платежу, бюджетні реквізити, підтвердження виконання.
- Розрахунок першої/другої половини — розподіл місячного нарахування, а НЕ окремий податковий розрахунок авансу. Для виплат авансу з одночасною сплатою податків і ЄСВ потрібна окрема логіка.
- Наразі ПСП — стандартний алгоритм для одного працівника без спеціального множення порога на кількість дітей, соціальних пільг іншого типу; ситуації з дітьми, інвалідністю, частковим місяцем, спецставками треба контролювати вручну.
- Платіжні інструкції стосуються окремого працівника та виду платежу, а не одного агрегованого документа за всіх співробітників. Нульові інструкції не створюються.
- Дані й проводки потребують інтеграційних тестів з Neon перед використанням у реальному обліку.
- Відредагувати вже проведений розрахунок заборонено. Виправлення здійснюються окремими коригувальними бухгалтерськими проводками, без затирання історії.
- `INSERT ... UPDATE` і бухгалтерські проводки проведення/підтвердження оформлено єдиним SQL-запитом на кожну операцію, що запобігає дублюванню при повторних запитах. Пакетна підготовка за кнопкою «Виплатити все» створює інструкції по черзі — у випадку мережевої помилки частина інструкцій може вже бути підготовлена.

## Перевірено
- `node --check` для всіх JS-файлів.
- Браузерний smoke-тест на тестових даних: поділ зарплати, річні податкові ставки, зарплатна відомість, кнопки підготовки інструкцій.
- Не виконувалися інтеграційні тести з реальним Neon, зовнішнім банком або друкованими шаблонами на різних принтерах.
